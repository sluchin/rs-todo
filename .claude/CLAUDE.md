## コミットガイドライン

- コミットメッセージは英語で記述
- **件名は、Conventional Commits の形式で書く**: `type(scope): description`。scope (括弧を含む) は、省略できる。description は、英語で、命令形 (例: `feat(task): Add the due date to a task`)。
  - type は、次のどれか。
    - `feat`: 機能の追加
    - `fix`: バグの修正
    - `docs`: 文書とコメントだけの変更 (`*.md`、ソースのコメント)
    - `style`: 整形、規約の適用 (動作を変えない)
    - `refactor`: 動作を変えない、書き換え
    - `test`: テストだけの変更
    - `build`: ビルドと、開発環境の変更
    - `ci`: CI (`.github/`) の変更
    - `chore`: そのほかの雑務 (最初のコミット、`.gitignore` など)
  - scope は、変更の場所を表す短い名前 (例: `task`)。決まった一覧はない。
  - 互換性を壊す変更は、type (または scope) の直後に、感嘆符を付ける (Conventional Commits の仕様のとおり)。
  - 複数の type にまたがるときは、変更の中心になる type にする。
- 件名のあとに空行を 1 行入れて、本文を書く。本文はダッシュ/ハイフンで始まる箇条書き (例: `- Fix bug in parser`)。箇条書きの各行の間には、空行を入れない
- コミットメッセージに `Co-Authored-By` または Claude 帰属行を含めない
- **rebase したあとの push は、`git push --force-with-lease --force-if-includes origin <ブランチ名>` で行う** (`--force` は使わない。リモートに、手元に取り込んでいないコミットがあれば、push は失敗する)。ユーザーに依頼されたときだけ、push する。

## テストの規約

- **Rust のテストは, `src-tauri/tests/` にファイルを分けて置く** (本番のソースの中に `#[cfg(test)] mod tests` を書かない). テストが呼ぶ関数は `pub` にして, `rstodo::commands::*` から使う. 名前は `test_<対象の関数名>_<内容>`. ファイルを使うテストは `tempfile` を使う.

## 開発ルール

- Markdown (`*.md`) の日本語の文章は、句読点に「、」「。」を使う (「,」「.」は使わない)。インラインコード・コードブロック・URL・ファイル名・数値 (`1.2.0`、`1,000`) は対象外。
- Markdown のコードブロック (3 つのバッククォートで囲んだ部分) の中の日本語は、ソースのコメントと同じく、句読点に「, 」「.」を使う。記号は、なるべく半角にする (`()` `""` `->` `<-` `~` `x` `>=` など)。罫線の図 (`─` `│` `▶` など) の中の矢印は、図がずれるので、そのままにする。見出しや番号付きリストの「1.」の形は変えない。`docs/` の生成物と、この `CLAUDE.md` は対象外。
- Markdown (`*.md`。この `CLAUDE.md` を除く) には、AI の目線の記述を書かない。読み手 (人) に向けて、事実、仕様、手順だけを書く。「承認されたら実装します」「教えてください」「提案します」のような、AI からの依頼や約束、作業の報告、「Claude が」のような書き手の記述は、会話で伝えて、ファイルには残さない。
- Markdown (`*.md`) を書く・直すときは、本多勝一著『日本語の作文技術』の原則 (修飾語の順序、ねじれのない係り受け、簡潔な一文一義など) を、厳密に守って、ドキュメントをブラッシュアップする。
  - 修飾語は、長いものを前に、短いものを後ろに置く。句点・読点は、係り受けを区切る所だけに打つ (余分な読点を入れない)。
  - 主語と述語を対応させて、ねじれをなくす。1 つの文には、1 つのことだけを書く (長い文は、分ける)。
  - 冗長な説明、くり返し、読み手の役に立たない補足は、削る。
